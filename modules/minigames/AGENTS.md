# minigames module guide

## Purpose
This module provides eleven server-validated skill-check minigames -- lockpick, skillbar, circuit, mash-key, fishing, pinpad, quiz, wordguess, wordscramble, keys, and hacking -- for gating real gameplay actions (picking a real lock, fishing, hacking a real terminal) where a purely client-side pass/fail would be trivially bypassable by a modified client. The server independently generates every round's solution and validates every submitted attempt; the client only ever renders the puzzle and reports raw input timestamps/selections. The last six types exist to back `compat/client/qb-minigames.lua` -- a drop-in shim for the real `github.com/qbcore-fivem/qb-minigames` resource's exports, which are pure client-trust; see "Legacy compat" below for how that gap is bridged.

## Public API
- `Kora.minigames.play(gameType, opts, authorization?)` (client) -- plays one round-based session for `"lockpick" | "skillbar" | "circuit" | "mash" | "fishing" | "pinpad" | "quiz" | "wordguess" | "wordscramble" | "keys" | "hacking"`. Without an authorization, `opts` is client-controlled, bounded/clamped server-side, and the result is deliberately proof-less. With an authorization, client `opts` is ignored and the server uses the trusted configuration captured when the authorization was issued. Returns the resolved `{ success, attempts, proof?, cancelled?, faults? }` table directly; callers do not need `Citizen.Await`.
- `Kora.minigames.playSkillCheck(skill, gameType, opts?, authorization?)` (client) -- the optional qbskills-aware form of `play`. It uses the local skill cache for presentation-only checks and is a no-op adjustment when kora_skills is stopped.
- `Kora.minigames.authorizeProof(src, gameType, trustedOpts?)` (server) -- resolves/copies trusted puzzle options and returns an opaque, resource-owned, single-use authorization for that player and game type.
- `Kora.minigames.authorizeSkillCheck(src, skill, gameType, trustedOpts?)` (server) -- resolves trusted options, obtains the player's configured kora_skills adjustment when available, and captures that result in the single-use authorization. Use this version for a valuable skill-gated action.
- `Kora.minigames.consumeProof(src, proof, gameType, authorization)` (server) -- consumes an authorized success proof only when issuer resource, player, game type, authorization, and TTL match. Mismatches do not burn a valid proof.
- `Kora.minigames.triangleWave(elapsedMs, speedHz)` (shared) -- deterministic renderer/server motion formula.

## Implementation notes
- **File layout**: `shared.lua` + `client.lua` + `server.lua`, unlike `modules/zones`/`modules/raycast` (client-only) -- this module genuinely needs both realms, since the server holds the puzzle solution and the client only renders/reports input.
- **`Kora.minigames.triangleWave` lives in `shared.lua`, attached to `Kora.minigames`, not left as a local**: `client.lua` and `server.lua` are separate Lua chunks within the same realm, so a plain `local function` in `shared.lua` would be invisible to both of them. Attaching it to `Kora.minigames` is what makes it visible to both files that load after it (same reasoning `modules/loops/shared.lua`'s `Kora.loops.controlled` is attached rather than kept local) -- and it's the one piece of logic that MUST be byte-identical between the client's renderer and the server's validator: the server checks a submitted attempt by recomputing the exact position the client was rendering at a given elapsed time, using this same formula. `build/finalise.lua` auto-exports it as `minigames_triangleWave`, which is harmless (it's a pure, stateless function -- there's nothing to protect by hiding it).
- **Only the intentional proof APIs are server exports**: generation, validation, session creation, and callback handlers remain local. `authorizeProof` and `consumeProof` are public because the gameplay resource must establish and later verify the capability boundary; neither exposes a solution or permits direct session creation.
- **Anti-cheat: report timestamps, never positions**: the client never computes or sends a pass/fail judgment, and for lockpick/skillbar it never sends a position either -- only *when* an input happened (`elapsed` milliseconds since the round started), plus for `circuit` *which* nodes were connected. The server independently recomputes correctness from its own stored `solution` and the shared `triangleWave` formula. This is a **floor, not full anti-cheat**: a scripted client can fabricate plausible input. Proof authorization prevents a client from choosing an easier proof-producing configuration or minting a generic proof, but the gameplay resource must still re-check its own live action constraints when consuming it.
- **`LockpickGame.tsx`'s per-pin "got it" highlight is cosmetic only**: on each press it locally recomputes `triangleWave(pressElapsed, puzzle.speed)` against `pin.target`/`puzzle.tolerance` -- the exact same public fields the puzzle payload already carries -- purely to color that pin's track green. It does not change what's reported (`presses` is still only `{ index, elapsed }` pairs) and the server's own recomputation from its hidden `solution` remains the sole source of truth for pass/fail; a modified client could always render this differently (or not at all) without affecting the real result either way.
- **Basic timestamp-plausibility checks**, applied by every `validate.*` function: timestamps must be non-negative, within the round's `timeLimit`, and spaced at least `Config.minigames.<type>.minTimePerPin`/`minReactionTime`/`minTimePerConnection`/`minPressInterval` apart -- fixed anti-cheat floors read directly from `Config`, **never** client-adjustable via `opts` (unlike the difficulty fields, which are clamped-but-adjustable).
- **`opts` is attacker-controlled unless captured by an authorization**: an unauthorized `play` forwards client `opts`, so every numeric field is finite-checked/clamped and every string/array is bounded. `authorizeProof` instead runs `resolveConfig` on the server caller's trusted options and stores the resulting copy; an authorized start ignores the client `opts` argument entirely. Keep all new option normalization in `resolveConfig` so both paths receive the same structural bounds.
- **Every client-provided collection must use `denseArrayLength` before iteration**: never rely on `#` or `ipairs` for attacker tables. String lengths are byte limits from `Config.minigames.inputLimits` (or a small protocol constant for fixed IDs/codes), and every numeric/timestamp check must reject NaN and infinities via `isFiniteNumber`/`assertElapsed` before arithmetic.
- **Callback quotas are part of the allocation boundary**: start/submit/cancel registrations must retain their `Config.minigames.callbackRateLimits` options. The shared callback layer rejects excess per-player calls before these handlers resolve configs, validate attacker arrays, or regenerate puzzles.
- **Anti-farming: every failed attempt regenerates a fresh solution**, including a malformed/short one, before the next round is offered (see the `submit` handler in `server.lua`). Reusing the same target between attempts would let a player who fails once simply memorize and repeat the exact spot, trivializing the skill check.
- **A malformed attempt counts as a failed attempt, not a protocol error**: the `submit` handler `pcall`s the type's `validate` function -- a thrown `assert` (wrong shape, wrong count, out-of-order presses) is treated identically to a legitimately-failed puzzle, consuming one attempt rather than rejecting the whole `Kora.callback` round trip.
- **One overlay for the whole session, not one per attempt**: `client.lua`'s `beginPlay` opens NUI focus once via `Kora.nui.withFocus` and loops `Kora.callback.trigger`/`Kora.nui.request` calls inside it -- a failed attempt with tries remaining re-renders the *same* mounted `MinigameContainer` with a fresh puzzle, it never closes and re-opens the overlay between rounds.
- **Do not drive the whole React tree at animation-frame frequency**: round expiry uses one browser timeout, and visible whole-second countdowns update four times per second. Only lockpick and skillbar need animation frames; those loops update the indicator element directly while React handles the slower semantic state changes. Keep future minigames on the same split unless their gameplay genuinely changes React-rendered content every frame.
- **The round's own `Kora.nui.request` uses a finite timeout** (`round.timeLimit + Config.minigames.roundTimeoutBuffer`), not `timeout = false` like the human-paced dialogs in `modules/nui` (menus, input forms). Unlike those, a minigame round is inherently time-limited by design -- the NUI component is expected to auto-submit whatever partial/empty attempt it has once its own on-screen timer runs out, well before this Lua-side timeout would ever fire. The finite bound exists as a safety net (a buggy or crashed NUI component can't hang the coroutine forever) and, as a side effect, is what lets an abandoned session (see below) self-terminate instead of leaking a suspended coroutine indefinitely.
- **Ownership is established at server authorization time, not inferred from the client callback**: `GetInvokingResource()` is meaningful in `authorizeProof`, so the authorization records that issuer. Authorized sessions and proofs inherit it and use separate `Kora.resources.serverRegistry` instances for resource-stop cleanup. Legacy sessions have no server resource owner and remain player/TTL scoped. All authorization/session/proof state is also removed on `playerDropped`.
- **Capability consumption order is security-sensitive**: an authorization is consumed only after issuer-independent player/type/expiry checks and puzzle generation succeed; a proof is consumed only after issuer/player/type/authorization/expiry all match. Mismatched requests must return/reject without deleting the valid token. Expired tokens may be deleted immediately.
- **Session TTL has two enforcement paths**: every round gets at least `Config.minigames.sessionTTL`, or its `timeLimit + roundTimeoutBuffer` when longer. That deadline refreshes on a retry but never exceeds the session's absolute bounded deadline. `expiresAt` is checked synchronously on every `submit` call (so a stale-but-still-submitted attempt fails cleanly), and a coarse 30-second `CreateThread` sweep separately reclaims any session nobody ever submits against again (an abandoned overlay, a crashed client, a calling resource that stopped without the player disconnecting) -- without the sweep, that session would sit in the server's `sessions` table forever.
- **Player-initiated cancel is a third, immediate path**: every minigame Dialog resolves `{ cancelled = true }` on Escape/backdrop (the same vocabulary `modules/nui`'s own menus use), which `client.lua`'s round loop checks for BEFORE calling `submit` -- a cancel never reaches `validate.*` and never consumes an attempt. It calls the dedicated `kora_lib:minigames:cancel` callback, which ends the session right away rather than leaving it for `expiresAt`/the sweep; without that, a player who cancels and immediately calls `Kora.minigames.play()` again would spuriously hit the `maxConcurrentPerPlayer` guard until the old session's TTL happened to lapse. A round that instead simply times out (`attempt == nil`) is unaffected by this -- it still falls through to `submit` and counts as a normal failed attempt, exactly as before this existed.
- **Failed client round-trips also cancel best-effort**: once `start` returns a session ID, a rejected NUI or callback promise triggers a best-effort `cancel` before the client promise rejects. The server also reclaims that player's synchronously-expired sessions before applying its concurrency ceiling, so neither a browser fault nor the coarse sweep cadence blocks an immediate valid retry.
- **Client-side resource-stop cleanup is best-effort, not a hard cancel**: `client.lua`'s `minigameOwnership` registry (`Kora.resources.registry`, tracking the LOCAL overlay/focus state -- not the server session) can drop the `activeSession` guard, release NUI focus, and close the overlay the instant the calling resource stops, but it cannot force the coroutine suspended inside `beginPlay`'s `Citizen.Await` calls to unwind -- Lua has no coroutine-cancellation primitive for that. The abandoned coroutine terminates on its own once its pending promise settles or times out (every `Kora.callback.trigger` and the round's `Kora.nui.request` have finite timeouts), it simply has no one left to hand its result to. This mirrors `modules/zones`' own zone creator, which has no deeper cancellation story for its in-flight confirm dialog either.
- **Circuit's colors ARE the answer key**: `generate.circuit` Fisher-Yates shuffles which color lands on which input/output pair, then sends every node's color to the client -- correctness is visually inherent (connect matching colors), so there's no separate mapping that would need to stay secret (and couldn't, since the client is the one rendering the puzzle).
- **The six qb-minigames-compat types differ on what stays hidden**: `pinpad`'s digits, `quiz`'s per-question `answer`, and `wordguess`'s/`wordscramble`'s actual word are kept in `solution` and never sent as `public` -- correctness genuinely can't be graded client-side for these (unlike lockpick/circuit, where the target IS shown and the skill is timing, not secrecy). `keys` and `hacking` instead reveal their full solution in `public` (the arrow pattern, the hex code) exactly like lockpick's target zones, since the player has to see what to do -- the skill there is reacting/typing correctly under time pressure, not finding a hidden answer.
- **`keys` always "succeeds"**: `validate.keys` returns `true, faults` unconditionally (never `false`) -- it mirrors upstream `KeyMinigame`, which has no pass/fail concept of its own; the calling script decides what `faults` count is acceptable (see the real resource's README: `if result.faults > 3 then ...`). `resolveConfig.keys` hard-codes `attempts = 1` accordingly -- there is nothing to retry.
- **`hacking` is a deliberate simplification of upstream**: the real qb-minigames `Hacking` renders two simultaneous overlapping hex-grid panels (WASD + arrow keys) the player must independently navigate to a hidden code. This module's `hacking` type is one revealed code the player types in before the countdown ends -- same params (`solutionsize`, `timeout`) and boolean return, deliberately simpler mechanic. `resolveConfig.hacking` also hard-codes `attempts = 1`, matching upstream's single pass/fail-against-a-countdown shape.

## Legacy compat (qb-minigames)
`compat/client/qb-minigames.lua` keeps `exports['qb-minigames']:Hacking/KeyMinigame/Lockpick/StartPinpad/Quiz/Skillbar/WordGuess/WordScramble` working for scripts written against the real `github.com/qbcore-fivem/qb-minigames` resource, by translating each call onto `Kora.minigames.play` and reshaping the result to upstream's exact return shape (same `provide '<name>'` + `__cfx_export_` identity-hijack pattern as `compat/client/qb-menu.lua`). Two calls carry a documented mechanic divergence rather than a 1:1 port:
- **`Lockpick(pins)`**: upstream's `pins` (its own README calls it "number of tries") maps onto kora_lib's `pinCount`, close in spirit (more pins = harder) but not the same tumbler minigame upstream ships.
- **`Skillbar(difficulty, validKeys)`**: `difficulty` maps onto a `zoneSize` (smaller = harder); `validKeys` has no equivalent in kora_lib's triangle-wave skillbar and is dropped, with a one-time console warning -- same "drop what can't be faithfully translated" precedent `compat/client/qb-menu.lua`'s `imageFor` sets for icons it can't map.

Every other export (`Hacking`, `KeyMinigame`, `StartPinpad`, `Quiz`, `WordGuess`, `WordScramble`) maps directly onto this module's matching new type with no divergence beyond the underlying anti-cheat model itself: upstream trusts the client's own pass/fail; here the server always decides.

## Best practices
- For valuable actions, issue a resource-owned authorization with trusted options, pass it as `play`'s third argument, and require `consumeProof` plus fresh resource-specific server checks before applying effects. Never authorize an effect from client `success = true` alone.
- Keep unauthorized `opts` to UX/difficulty tuning only. The anti-cheat timing floors and hard input limits are intentionally not overridable.
- Don't call `Kora.minigames.play` again for the same player while a previous call's promise is still pending -- it will reject immediately (client-side guard, backed by a server-side check in case a modified client skips it) rather than queue.

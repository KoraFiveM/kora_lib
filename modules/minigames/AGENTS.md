# minigames module guide

## Purpose
This module provides ten server-validated skill-check minigames -- lockpick, skillbar, circuit, mash-key, pinpad, quiz, wordguess, wordscramble, keys, and hacking -- for gating real gameplay actions (picking a real lock, hacking a real terminal) where a purely client-side pass/fail would be trivially bypassable by a modified client. The server independently generates every round's solution and validates every submitted attempt; the client only ever renders the puzzle and reports raw input timestamps/selections. The last six types exist to back `compat/client/qb-minigames.lua` -- a drop-in shim for the real `github.com/qbcore-fivem/qb-minigames` resource's exports, which are pure client-trust; see "Legacy compat" below for how that gap is bridged.

## Public API
- `QB.minigames.play(gameType, opts)` -- plays one round-based session for `"lockpick" | "skillbar" | "circuit" | "mash" | "pinpad" | "quiz" | "wordguess" | "wordscramble" | "keys" | "hacking"`. `opts` is an optional table of per-type overrides (see docs.md), merged over `Config.minigames.<type>` and clamped/validated server-side regardless of what the client sends. For `pinpad`/`quiz`/`wordguess`/`wordscramble`, `opts` also carries the puzzle's actual CONTENT (the PIN/questions/word) -- the caller supplies it, exactly like the real qb-minigames exports do, rather than the server randomizing it from config. Returns a promise resolving `{ success, attempts, cancelled?, faults? }` (`attempts` = how many tries it took; `cancelled` present when the player backed out via Escape/backdrop instead of succeeding or exhausting attempts; `faults` only ever present for `"keys"`, see below), or rejects if a minigame is already active for this player, `gameType` is invalid, or the round trip fails.
- That is the **only** function attached to `QB.minigames.*`, on either realm -- see "Server has no exports" below.

## Implementation notes
- **File layout**: `shared.lua` + `client.lua` + `server.lua`, unlike `modules/zones`/`modules/raycast` (client-only) -- this module genuinely needs both realms, since the server holds the puzzle solution and the client only renders/reports input.
- **`QB.minigames.triangleWave` lives in `shared.lua`, attached to `QB.minigames`, not left as a local**: `client.lua` and `server.lua` are separate Lua chunks within the same realm, so a plain `local function` in `shared.lua` would be invisible to both of them. Attaching it to `QB.minigames` is what makes it visible to both files that load after it (same reasoning `modules/loops/shared.lua`'s `QB.loops.controlled` is attached rather than kept local) -- and it's the one piece of logic that MUST be byte-identical between the client's renderer and the server's validator: the server checks a submitted attempt by recomputing the exact position the client was rendering at a given elapsed time, using this same formula. `build/finalise.lua` auto-exports it as `minigames_triangleWave`, which is harmless (it's a pure, stateless function -- there's nothing to protect by hiding it).
- **Server has no `QB.minigames.*` exports at all**: both `QB.callback.register` handlers (`qblib:minigames:start`, `qblib:minigames:submit`) and every generate/validate/session helper in `server.lua` are `local function`s (or entries in local `generate`/`validate`/`resolveConfig` dispatch tables), never `QB.minigames.xxx`. `build/finalise.lua` exports every function it finds under `pairs(QB.minigames)` with no allow-list -- attaching puzzle-generation internals there would hand any other resource direct access to session creation and solution generation, bypassing the `src`-scoping the callback names already enforce. Same reasoning `modules/zones`' creator internals stay local.
- **Anti-cheat: report timestamps, never positions**: the client never computes or sends a pass/fail judgment, and for lockpick/skillbar it never sends a position either -- only *when* an input happened (`elapsed` milliseconds since the round started), plus for `circuit` *which* nodes were connected. The server independently recomputes correctness from its own stored `solution` (never sent to the client) and the shared `triangleWave` formula. This is a **floor, not full anti-cheat**: a scripted/instrumented client that fabricates *plausible* timestamps (respecting the minimum-spacing/time-limit checks below) can still forge a pass. Document this limitation plainly to anything gating high-value actions on `QB.minigames.play` -- it raises the bar past a naive client-side check, it doesn't eliminate cheating.
- **`LockpickGame.tsx`'s per-pin "got it" highlight is cosmetic only**: on each press it locally recomputes `triangleWave(pressElapsed, puzzle.speed)` against `pin.target`/`puzzle.tolerance` -- the exact same public fields the puzzle payload already carries -- purely to color that pin's track green. It does not change what's reported (`presses` is still only `{ index, elapsed }` pairs) and the server's own recomputation from its hidden `solution` remains the sole source of truth for pass/fail; a modified client could always render this differently (or not at all) without affecting the real result either way.
- **Basic timestamp-plausibility checks**, applied by every `validate.*` function: timestamps must be non-negative, within the round's `timeLimit`, and spaced at least `Config.minigames.<type>.minTimePerPin`/`minReactionTime`/`minTimePerConnection`/`minPressInterval` apart -- fixed anti-cheat floors read directly from `Config`, **never** client-adjustable via `opts` (unlike the difficulty fields, which are clamped-but-adjustable).
- **`opts` is attacker-controlled, not just caller-controlled**: `QB.minigames.play(gameType, opts)` is a *client* function, so `opts` reaches the server over the network (via `QB.callback.trigger`) from whatever code is running on that player's client -- which could be a modified client calling the export directly, bypassing whatever legitimate resource intended. Every numeric field in `opts` is clamped to a hard range in `server.lua`'s `resolveConfig.*` functions (`clampNumber`/`clampInt`) rather than trusted outright; `attempts` is additionally capped at `Config.minigames.maxAttemptsCap` regardless of the per-type default or any override.
- **Anti-farming: every failed attempt regenerates a fresh solution**, including a malformed/short one, before the next round is offered (see the `submit` handler in `server.lua`). Reusing the same target between attempts would let a player who fails once simply memorize and repeat the exact spot, trivializing the skill check.
- **A malformed attempt counts as a failed attempt, not a protocol error**: the `submit` handler `pcall`s the type's `validate` function -- a thrown `assert` (wrong shape, wrong count, out-of-order presses) is treated identically to a legitimately-failed puzzle, consuming one attempt rather than rejecting the whole `QB.callback` round trip.
- **One overlay for the whole session, not one per attempt**: `client.lua`'s `beginPlay` opens NUI focus once via `QB.nui.withFocus` and loops `QB.callback.trigger`/`QB.nui.request` calls inside it -- a failed attempt with tries remaining re-renders the *same* mounted `MinigameContainer` with a fresh puzzle, it never closes and re-opens the overlay between rounds.
- **The round's own `QB.nui.request` uses a finite timeout** (`round.timeLimit + Config.minigames.roundTimeoutBuffer`), not `timeout = false` like the human-paced dialogs in `modules/nui` (menus, input forms). Unlike those, a minigame round is inherently time-limited by design -- the NUI component is expected to auto-submit whatever partial/empty attempt it has once its own on-screen timer runs out, well before this Lua-side timeout would ever fire. The finite bound exists as a safety net (a buggy or crashed NUI component can't hang the coroutine forever) and, as a side effect, is what lets an abandoned session (see below) self-terminate instead of leaking a suspended coroutine indefinitely.
- **Server session ownership is tracked by player, not by resource**: unlike `QB.zones.box()` or `QB.callback.register()`, `QB.minigames.play()` is called from the *client* and reaches `server.lua`'s callback handlers over a network event (`local/callback/server.lua`'s `events.invoke`), not via a direct cross-resource Lua call -- so `GetInvokingResource()` would be meaningless there (always `nil`; there is no in-progress exports() call to inspect at that point). Session cleanup is instead tied to the player via `AddEventHandler("playerDropped", ...)`, exactly like `local/callback/server.lua`'s own per-player token cleanup -- `QB.resources.serverRegistry` is deliberately **not** used here.
- **Session TTL has two enforcement paths**: `expiresAt` is checked synchronously on every `submit` call (so a stale-but-still-submitted attempt fails cleanly), and a coarse 30-second `CreateThread` sweep separately reclaims any session nobody ever submits against again (an abandoned overlay, a crashed client, a calling resource that stopped without the player disconnecting) -- without the sweep, that session would sit in the server's `sessions` table forever.
- **Player-initiated cancel is a third, immediate path**: every minigame Dialog resolves `{ cancelled = true }` on Escape/backdrop (the same vocabulary `modules/nui`'s own menus use), which `client.lua`'s round loop checks for BEFORE calling `submit` -- a cancel never reaches `validate.*` and never consumes an attempt. It calls the dedicated `qblib:minigames:cancel` callback, which ends the session right away rather than leaving it for `expiresAt`/the sweep; without that, a player who cancels and immediately calls `QB.minigames.play()` again would spuriously hit the `maxConcurrentPerPlayer` guard until the old session's TTL happened to lapse. A round that instead simply times out (`attempt == nil`) is unaffected by this -- it still falls through to `submit` and counts as a normal failed attempt, exactly as before this existed.
- **Client-side resource-stop cleanup is best-effort, not a hard cancel**: `client.lua`'s `minigameOwnership` registry (`QB.resources.registry`, tracking the LOCAL overlay/focus state -- not the server session) can drop the `activeSession` guard, release NUI focus, and close the overlay the instant the calling resource stops, but it cannot force the coroutine suspended inside `beginPlay`'s `Citizen.Await` calls to unwind -- Lua has no coroutine-cancellation primitive for that. The abandoned coroutine terminates on its own once its pending promise settles or times out (every `QB.callback.trigger` and the round's `QB.nui.request` have finite timeouts), it simply has no one left to hand its result to. This mirrors `modules/zones`' own zone creator, which has no deeper cancellation story for its in-flight confirm dialog either.
- **Circuit's colors ARE the answer key**: `generate.circuit` Fisher-Yates shuffles which color lands on which input/output pair, then sends every node's color to the client -- correctness is visually inherent (connect matching colors), so there's no separate mapping that would need to stay secret (and couldn't, since the client is the one rendering the puzzle).
- **The six qb-minigames-compat types differ on what stays hidden**: `pinpad`'s digits, `quiz`'s per-question `answer`, and `wordguess`'s/`wordscramble`'s actual word are kept in `solution` and never sent as `public` -- correctness genuinely can't be graded client-side for these (unlike lockpick/circuit, where the target IS shown and the skill is timing, not secrecy). `keys` and `hacking` instead reveal their full solution in `public` (the arrow pattern, the hex code) exactly like lockpick's target zones, since the player has to see what to do -- the skill there is reacting/typing correctly under time pressure, not finding a hidden answer.
- **`keys` always "succeeds"**: `validate.keys` returns `true, faults` unconditionally (never `false`) -- it mirrors upstream `KeyMinigame`, which has no pass/fail concept of its own; the calling script decides what `faults` count is acceptable (see the real resource's README: `if result.faults > 3 then ...`). `resolveConfig.keys` hard-codes `attempts = 1` accordingly -- there is nothing to retry.
- **`hacking` is a deliberate simplification of upstream**: the real qb-minigames `Hacking` renders two simultaneous overlapping hex-grid panels (WASD + arrow keys) the player must independently navigate to a hidden code. This module's `hacking` type is one revealed code the player types in before the countdown ends -- same params (`solutionsize`, `timeout`) and boolean return, deliberately simpler mechanic. `resolveConfig.hacking` also hard-codes `attempts = 1`, matching upstream's single pass/fail-against-a-countdown shape.

## Legacy compat (qb-minigames)
`compat/client/qb-minigames.lua` keeps `exports['qb-minigames']:Hacking/KeyMinigame/Lockpick/StartPinpad/Quiz/Skillbar/WordGuess/WordScramble` working for scripts written against the real `github.com/qbcore-fivem/qb-minigames` resource, by translating each call onto `QB.minigames.play` and reshaping the result to upstream's exact return shape (same `provide '<name>'` + `__cfx_export_` identity-hijack pattern as `compat/client/qb-menu.lua`). Two calls carry a documented mechanic divergence rather than a 1:1 port:
- **`Lockpick(pins)`**: upstream's `pins` (its own README calls it "number of tries") maps onto qblib's `pinCount`, close in spirit (more pins = harder) but not the same tumbler minigame upstream ships.
- **`Skillbar(difficulty, validKeys)`**: `difficulty` maps onto a `zoneSize` (smaller = harder); `validKeys` has no equivalent in qblib's triangle-wave skillbar and is dropped, with a one-time console warning -- same "drop what can't be faithfully translated" precedent `compat/client/qb-menu.lua`'s `imageFor` sets for icons it can't map.

Every other export (`Hacking`, `KeyMinigame`, `StartPinpad`, `Quiz`, `WordGuess`, `WordScramble`) maps directly onto this module's matching new type with no divergence beyond the underlying anti-cheat model itself: upstream trusts the client's own pass/fail; here the server always decides.

## Best practices
- Treat `QB.minigames.play`'s anti-cheat as a floor, not a guarantee -- pair it with server-side checks on whatever real action it gates (e.g. re-verify the player is actually near/interacting with the thing being lockpicked) rather than trusting a `success = true` result in isolation for anything high-value.
- Keep `opts` to genuine difficulty tuning (pin count, time limit, tolerance) -- the anti-cheat timing floors are intentionally not overridable, and nothing else in this module reads unrecognized `opts` fields.
- Don't call `QB.minigames.play` again for the same player while a previous call's promise is still pending -- it will reject immediately (client-side guard, backed by a server-side check in case a modified client skips it) rather than queue.

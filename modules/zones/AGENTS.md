# zones module guide

## Purpose
This module provides ox_lib-style trigger zones for the local player: box, sphere, and poly shapes with `onEnter`/`onExit`/`inside` callbacks, plus points as a thin convenience wrapper over sphere rather than a separate shape or module. It's built to stay cheap with many zones registered across many resources, not just correct.

## Public API
- `QB.zones.box(opts)` — `coords`, `size` (vec3 extents), `rotation` (degrees around Z, default 0), `onEnter`/`onExit`/`inside`, `debug`, `data`.
- `QB.zones.sphere(opts)` — `coords`, `radius`, `onEnter`/`onExit`/`inside`, `debug`, `data`.
- `QB.zones.poly(opts)` — `points` (array of vec3; XY defines the footprint), `thickness` or explicit `minZ`/`maxZ`, `onEnter`/`onExit`/`inside`, `debug`, `data`.
- `QB.zones.point(opts)` — `coords`, `radius` (defaults to `Config.zones.defaultPointRadius`), same callbacks. Internally just `createZone("sphere", opts, initSphere)` — it is not a parallel code path, and the resulting zone is indistinguishable from a plain sphere.
- Every constructor returns a handle (`QBZoneHandle` — the option/handle shapes are declared as `---@class` blocks above the constructors): `{ id, type, resource, data, remove(), contains(coords), isInside() }`.
- `QB.zones.startCreator(zoneType, existingOpts?)` — in-world interactive zone builder for `"box" | "sphere" | "poly"`, optionally seeded from an existing zone's opts (to reposition/resize it) via `existingOpts`. Returns a promise resolving `{ type, opts }` once confirmed (`opts` is directly usable as `QB.zones.<type>(opts)`), `nil` if cancelled, or rejecting if a creator is already running, `zoneType` is invalid, or `Config.zones.creator.enabled` is `false`.
- `QB.zones.getInside(resource?)` — every zone currently containing the player, optionally filtered to one owning resource. Returns the cached handles (see below), read off the tick loop's existing enter/exit state — no containment maths.
- `QB.zones.generateSnippet(zoneType, opts)` — pure formatter, `opts -> "QB.zones.<type>({...})"` string. Powers the creator's confirm dialog/clipboard copy, but doesn't need the creator running to call directly.

## Implementation notes
- **File layout**: everything lives in `client.lua` — no `shared.lua`, no `server.lua`. `modules/**/shared.lua` and `modules/**/client.lua` are separate Lua chunks (locals never cross files), and `build/finalise.lua` exports every function it finds under `pairs(QB.zones)` with no allow-list, so a private helper can't safely live as `QB.zones.xxx` either. `modules/stream/` has the same no-`shared.lua` shape for the same reason (client-only, nothing to share across environments).
- **Coordinates**: any vector-like input (`glm.vec3`, native `vector3`, `{x=,y=,z=}`) is normalized once through `toVec3` into a plain `{x=,y=,z=}` table, the canonical internal representation — not `glm.vec3`, since the `glm` global isn't guaranteed to exist on every FiveM client build. `distSq`/`containsBox` do their own component-wise subtraction (`a.x - b.x`, etc.) instead of relying on glm's operator overloads for vector subtraction.
- **Poly is 2D + height band, not 3D**: `points` define an XY footprint; `[minZ, maxZ]` (explicit, or derived from `thickness`) gives it vertical extent. Matches ox_lib's own model and is far cheaper than arbitrary-orientation 3D containment, which nothing here needs. `thickness` is anchored **upward from the lowest point**, not centred on the average: points are overwhelmingly placed by aiming at the ground (the in-world creator can only do that), so a centred band buried half the zone underground and left only `thickness/2` of headroom — and on sloping ground an average can sit above the lowest point's own floor, leaving a gap there.
- **Spatial grid**: one shared grid keyed on horizontal XY only (`Config.zones.gridSize`), not per-shape-type (location doesn't correlate with shape) and not Z-bucketed (rare case, already handled by each zone's own vertical range check). Cell keys are packed integers (`cx * 100000 + cy`), not strings, to avoid allocation on the tick hot path. A zone is inserted into every cell its horizontal AABB overlaps at creation, and removed from all of them on teardown (buckets that empty out are deleted, so grid memory doesn't grow unbounded on a churny server).
- **Per-tick lookup**: the 3×3 neighborhood of the player's current cell is unioned into a candidate list. Only the current cell is strictly required for correctness; the margin exists so the adaptive tick-rate's proximity check can notice a nearby zone just across a cell boundary before the player's cell actually changes.
- **The candidate list is memoized** on `(cell key, gridEpoch)`, and `gridEpoch` is bumped by `insertIntoGrid`/`removeFromGrid` — the only two functions that mutate the grid, which covers creation, teardown and `QB.zones.edit`'s re-insert alike. Its result only changes when the player crosses a 50m cell boundary or the grid itself changes; on foot that's roughly once every ten seconds, so rebuilding it per tick meant nine hash lookups, a set union and a discarded table to reach the same answer as last frame. It's cached as a dense ARRAY of zone REFERENCES rather than a set of ids, so the tick walks it by index with no second registry lookup per candidate. Because that array is a snapshot, liveness is re-checked per zone off the `zone.removed` flag `destroyZone` already sets — an `onEnter`/`onExit` handler is free to destroy another zone while the loop is still walking it.
- **The tick allocates nothing.** `GetEntityCoords`' vector3 is used directly instead of being copied into a `{x,y,z}` table (every reader only touches `.x`/`.y`/`.z`), and `aabbDistSq` inlines its clamp instead of materialising the nearest point on the AABB. Those two tables were ~500 bytes of garbage per tick, and this tick runs *per frame* whenever anyone stands in a zone with an `inside` callback. Keep it that way: anything allocated in `tickLoop` is allocated 60 times a second, forever.
- **`GetEntitySpeed` is only paid for when it can matter**: with no candidate in any neighbouring cell there is nothing to be near, so the far tier is taken without asking the engine how fast the player is going.
- **Cheap-reject before exact test**: every candidate gets an AABB-clamped squared-distance check first (nearest point on the box, not distance to center — matters for large/irregular zones where the edge is what's "near"). The exact shape test (`containsFn[zone.type]`: box rotation, polygon winding, sphere distance) only runs when that clamped distance is 0.
- **Box rotation**: plain cached `cos`/`sin` scalars from `-rotation`, not glm quaternions — cheaper per-check and doesn't depend on an unverified glm rotation API. `rotatedHalfExtents` reuses the same cached values for the box's world AABB; the `abs()` in that formula makes the `-rotation` vs `rotation` sign convention irrelevant there.
- **Adaptive tick rate**: `Config.zones.tickInside` (0ms) while inside a zone with an `inside` callback, `Config.zones.tickNear` (200ms) when a candidate is within the proximity threshold or inside a zone with no `inside` callback, `Config.zones.tickFar` (1000ms) otherwise. The near threshold is widened by `GetEntitySpeed(ped) * (tickFar/1000) * Config.zones.speedSafetyFactor` so a vehicle moving fast enough to cross the base threshold between two far-tier ticks doesn't skip a small zone entirely.
- **Lazy threads**: the tick thread only starts on first zone creation (`ensureTickThread`); the debug-draw thread only runs while at least one debug zone exists and stops itself once none remain. A server that never touches `QB.zones.*` pays nothing.
- **Debug rendering is one plain `DrawLine` per edge plus filled walls**, not a thickened wireframe -- the walls (below) are what make a debug zone easy to spot, so there's no need to also fake line width or draw corner markers on top of them.
- **Debug walls**: `drawWallQuad`/`drawWallTriangle` fill each box face (6, via `BOX_FACES`) and each poly edge's vertical side (one per edge, no top/bottom caps -- an arbitrary footprint isn't guaranteed convex, and properly triangulating one is more complexity than a debug-only visual needs) with translucent `DrawPoly` triangles, at `Config.zones.debugWallAlpha` rather than the wireframe colour's own alpha so the fill doesn't bury the wireframe it's layered under. `DrawPoly` is single-sided (backface-culled), so every triangle is drawn twice with the last two vertices swapped -- otherwise a wall facing away from the camera (routine when you're standing inside the zone, which is often exactly when you're debugging one) would simply not render.
- **Debug colour follows the shared UI accent, not a fixed value**: both `ensureDebugThread`'s loop and the creator's live preview draw call `zoneDebugColor()` (next to `wallColor`) instead of reading a static `Config.zones.debugColor` -- it converts `QB.theme.accentColor()` (already validated/defaulted, see `modules/theme/`) to RGB via `hexToRgb` and pairs it with `Config.zones.debugAlpha`, so a debug zone's wireframe/walls and the creator's own preview always match the rest of qblib's NUI rather than carrying their own hardcoded red.
- **The handle is built once and cached on the zone** (`zone.handle`) rather than rebuilt per call, so `QB.zones.getInside()` returns the identical table the constructor handed back — a consumer can `==` compare it against its own reference, and there's no risk of a second handle carrying a stale `data` field.
- **Callback isolation**: `onEnter`/`onExit`/`inside` run through `safeCall` (`pcall`, log-and-continue on error) rather than pcall-then-rethrow like `modules/stream` — one shared thread drives every zone from every resource, so one resource's buggy callback must not break enter/exit tracking for anyone else's zones.
- **No `onExit` on forced cleanup**: a zone removed via `remove()` or an `onClientResourceStop` sweep does not fire `onExit` even if the player was inside it — the owning resource is gone/removing itself, so there's nothing meaningful to call back into.
- **Resource ownership**: `GetInvokingResource() or GetCurrentResourceName()` is captured at creation time. Because consumer resources reach `QB.zones.*` through `exports.qblib` via the `QB` proxy in `init.lua`, `GetInvokingResource()` correctly identifies the calling resource from inside qblib's own environment. Ownership tracking itself is delegated to `QB.resources.registry` (`local/resources`) rather than hand-rolled here. A single `destroyZone` teardown is shared by manual `remove()` calls and the registry's own resource-stop sweep (which calls back into `destroyZone` via its `onDispose`) — `destroyZone` and the registry are mutually forward-declared locals since each needs to reference the other.
- **Zone creator (`QB.zones.startCreator`)**: everything lives in the same `client.lua`, in a section below the tick loop.
  - **Placement is a raycast, not typed coordinates**: `raycastFromCamera` aims from `GetGameplayCamCoord`/`GetGameplayCamRot` and hit-tests with `StartShapeTestRay`/`GetShapeTestResult` — the placement key just marks wherever the player is currently looking. This is the whole point of building this instead of a form: no coordinate typing, no menu-driven placement fighting the camera.
  - **The creator flies its own scripted freecam, not the gameplay camera**: `beginCreator` calls `startCreatorCamera` (before `ensureCreatorThread`, so `state.cam` exists before any keybind handler could possibly run) to spin up a `DEFAULT_SCRIPTED_CAMERA` seeded from wherever the gameplay camera already was, then `RenderScriptCams(true, true, Config.zones.creator.cameraTransitionMs, true, true)` blends into it and `FreezeEntityPosition` roots the player in place. A `QB.controls` lease suppresses mouse-look/WASD controls 1/2/30/31 while `GetDisabledControlNormal` drives `state.camYaw`/`state.camPitch`/`state.camCoords` every frame, at `Config.zones.creator.cameraMoveSpeed`/`cameraLookSensitivity` (Shift boosts movement by the same `Config.zones.creator.shiftMultiplier` the size/rotation scroll-step already uses — one speed knob, not two). Teardown releases that lease on confirm, cancel, error, or owner shutdown. The radar/HUD restore synchronously in the same tick the per-frame loop exits (an existing test asserts this happens within one `net.step()`), but the camera's own `RenderScriptCams(false, ...)` ease-out + `DestroyCam` run in a separate short-lived thread so the visual blend back to the gameplay camera isn't cut short by that synchronous restore. `QB.raycast.fromCam(state.cam, ...)` replaces `QB.raycast.fromCamera(...)` at both of the creator's own aim/placement call sites (inside `creatorPlace` and the per-frame aim-reticle marker) — the gameplay camera plays no role in the creator anymore. Reason for a dedicated camera at all: it lets the player survey a build site from angles walking wouldn't reach.
  - **Discrete actions use `QB.keybind`** (place/undo/cycle-parameter/confirm/cancel), not raw `IsControlJustPressed` polling — keeps every action rebindable through FiveM's own keybind settings. Scroll wheel (controls 14/15) is the one thing still polled per-frame, since mouse wheel isn't a key-mappable input here.
  - **Editing poly points is a pick-up/drop, not a single click**: cycling to the `"editPoint"` entry makes the place key (E) a two-step action tracked by `state.grabbing` — the first press grabs whichever point `state.editIndex` is currently hovering (frozen there; the per-frame loop stops re-tracking `editIndex` from the aim while `grabbing` is true), then the player can fly the freecam anywhere, and a second press drops the grabbed point at the *new* aim and clears `grabbing`. Undo (Backspace) cancels an in-progress grab instead of deleting the last placed point, since that point is very likely a different one from whatever's being carried. This exists because the natural single-click "move nearest point to current aim" can't express "carry this one specific point over there" at all — the instant the camera turns away from a point, it's no longer nearest its own aim, so there was no way to select a point and then reposition the camera before confirming where it goes. The grabbed marker is drawn following the live aim (not the point's last confirmed position) and in a distinct colour from the hover highlight, so the two states read differently on screen.
  - **`shiftHeld()` OR's raw-key and control-based detection instead of preferring one**: `IsRawKeyDown(16)` can execute without erroring yet still never report a real Shift press on some client builds (its raw key codes don't reliably line up with the generic VK_SHIFT constant), and a `pcall` can't distinguish "the native is missing" from "the native ran and says false" — trusting a clean `false` from it unconditionally silently disabled Shift detection (movement speed boost, scroll-step multiplier) entirely on those builds. `IsControlPressed(0, 21)` (Sprint, bound to Shift by default) is now checked unconditionally as a second signal rather than only on a `pcall` failure.
  - **One adjustable parameter at a time**: `creatorParamCycles` lists each shape's numeric parameters (box: size/height/rotation; sphere: radius; poly: thickness); the cycle key advances `state.activeParam` and the scroll wheel adjusts whichever one is currently active. Chosen over modifier-key chords (hold-Alt-to-resize, etc.) specifically for discoverability — the HUD always shows which parameter scroll currently controls.
  - **Live preview reuses the real containment/debug-draw code**: `buildPreviewZone` runs the in-progress shape's state back through `initBox`/`initSphere`/`initPoly` (the exact functions real zones are built with) into a scratch table, then `drawDebugFn[type]` draws it — so what you see while placing is pixel-identical to a normal `debug = true` zone, not a separate lookalike renderer.
  - **Pending poly points are drawn separately, in red**: a poly can't preview until it has 3 points (`buildPreviewZone` defers to `creatorCanConfirm`), so the first two placements would otherwise leave the screen unchanged and the player couldn't tell the keypress had registered at all. Each placed point is drawn as a red sphere marker while `#points < 3`, then stops — the real preview's own debug draw already marks every vertex from that point on. The markers carry `state.zOffset` like everything else, so a raised poly's pending points sit at the finished zone's floor rather than back on the ground.
  - **Seeding from an existing zone** (`seedCreatorState`): `startCreator(type, existingOpts)` maps `existingOpts` (the same shape `QB.zones.<type>()` takes) onto the fresh creator state before it starts — box/sphere copy `coords`/`size`/`radius`/`rotation` directly (a non-square seed box's `size.y` is dropped, since the creator only tracks one uniform X/Y size scalar — the player can still adjust it afterward), poly copies `points` and derives `thickness` from `maxZ - minZ` when those are given instead of a bare `thickness`. Any field not present in `existingOpts` keeps `newCreatorState`'s usual default.
  - **The creator never registers a live zone**: confirming resolves `{ type, opts }` and tears down the scratch preview. The caller can use the returned options to create a runtime zone explicitly, but the builder itself exists only to capture coordinates/configuration and must not leave an ownerless zone behind.
  - **Resource ownership across an async gap**: `startCreator` captures `GetInvokingResource() or GetCurrentResourceName()` synchronously, before returning its promise — by the time the session is cancelled or confirmed (seconds/minutes later, via a keypress with no exports call in progress), `GetInvokingResource()` would just return `nil`. The captured resource lets `onClientResourceStop` cancel a creator whose owning consumer stops while the session is active.
  - **Confirm dialog blocks its own coroutine, not the preview thread**: `openConfirmDialog` runs inside whatever coroutine called it (a `RegisterCommand` handler) and `Citizen.Await`s the NUI response directly — it does not touch the separate per-frame preview thread, which keeps running (and keeps drawing the now-frozen shape) independently. Game input stops reaching either one anyway once `QB.nui.withFocus` grants the NUI keyboard+mouse focus.
  - **HUD updates are change-gated**: the preview thread runs every frame (`Wait(0)`, for smooth raycasting/drawing), but only calls `QB.nui.send("zoneCreator:hud", ...)` when the snapshot actually differs from the last one sent (`hudSnapshotsEqual`, a plain field-by-field comparison, not `json.encode` — cheaper for a small flat table that's compared far more often than it's actually sent) — avoiding a 60Hz message flood over something that mostly doesn't change frame to frame.
  - **The preview shape itself is cache-and-dirty-gated, not rebuilt every frame**: unlike the HUD snapshot (cheap to rebuild, so it's rebuilt every frame purely for comparison), `buildPreviewZone` re-runs `initBox`/`initSphere`/`initPoly` — real allocations, and for poly an O(N) sweep over every placed point. `state.dirty` is set only by the three mutators that can actually change the shape (`creatorPlace`, `creatorUndo`, `adjustActiveParam`); the per-frame loop only rebuilds `state.cachedPreview` when `state.dirty`, and just redraws the cached one otherwise. Cycling the active parameter (`creatorCycleParam`) deliberately does *not* set `dirty` — it changes which field scroll adjusts, not the shape itself.
  - **Confirm/cancel share one `resolveCreator(value)`**, not two near-identical functions — a confirm resolves `{ type, opts }`, a cancel resolves `nil`, and both otherwise do the same teardown.
  - **The five keybinds share one `registerCreatorKeybind(command, label, key, handler)`** rather than five copies of the same `QB.keybind.add` + "only run if a creator is active" boilerplate.
  - **Disabling the creator**: `Config.zones.creator.enabled = false` makes `QB.zones.startCreator` reject immediately (checked before the "already running" guard) — the `qblib_zonecreator_*` keybind commands still get registered either way (they're no-ops without an active `creatorState`, and `creatorState` can only ever be set via `startCreator`), so there's nothing else to gate.

## Best practices
- Keep `inside` callbacks cheap — they can run every frame while the player is inside that zone.
- Don't rely on zone iteration order; the grid/candidate set is unordered.
- Prefer `poly` with a tight `minZ`/`maxZ` over a tall `thickness` default when a footprint spans multiple floors — a thinner height band means fewer false-positive AABB candidates near it.
- Use `debug = true` only during development — it's not part of the optimization path and draws every frame while active.

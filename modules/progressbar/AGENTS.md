# progressbar module guide

## Purpose
Runs a timed, cancellable "the player is busy doing X" bar: shows a fill bar in the NUI, optionally plays an animation, optionally disables controls, and reports whether it ran to completion. Client-only, same reasoning as `modules/nui`/`modules/zones`/`modules/stream` — nothing here crosses the client/server boundary, so no `shared.lua`/`server.lua`.

## Public API
- `QB.progressbar.start(payload)` — see `docs.md` for the full payload shape. Returns `completed, error` (`error` set only for the reject-immediately "already active" case, never for a normal cancellation).
- `QB.progressbar.cancel()` — flags the active bar to stop on its next tick. Returns whether anything was actually running.
- `QB.progressbar.isActive()` — whether a bar started by this module is currently running.

## Implementation notes
- **Lua owns timing, the NUI is purely visual.** `QB.nui.send("progressStart", { label, duration })` is fire-and-forget — there is no `QB.nui.request` round trip, and the NUI never reports completion back. The actual pass/fail decision is made entirely client-side by `QB.loops.controlled`'s predicate; the NUI's own CSS fill animation (`web/src/components/progressbar/ProgressBar.tsx`) just happens to be timed to the same `duration`. `QB.nui.send("progressCancel")` (no payload) is sent on every early-exit path so the visual can't outlive the real state (still filling after the bar it represents already ended).
- **`QB.loops.controlled`'s "Loop timed out" IS the success path here** — inverted from how every other caller of it (`modules/stream`, `local/events`) uses it. The predicate passed to it returns truthy ONLY to signal "cancel now"; running the full `duration` without it ever doing that is exactly what "completed" means. Don't "fix" the polarity without also re-reading `modules/loops/shared.lua`'s doc comment.
- **Exclusive by design, not by accident.** `busy` is a single module-level flag, not a queue or a resource-owned registry entry like `modules/blips`/`modules/cache` use — a progress bar has no persistent handle, and only one can ever meaningfully be running at once (which animation plays, whose `disable` wins if two were allowed to overlap). `QB.progressbar.start` called while `busy` is true fails immediately with `completed = false, error = "..."` rather than queuing, replacing, or interrupting the running one.
- **`cancelRequested` is checked, not acted on, inside the poll loop.** `QB.progressbar.cancel()` just sets a flag; the loop's own predicate (running every frame regardless) is what actually ends the bar. This is deliberate — there is no synchronous "stop right now" path, so a caller that needs to know the bar actually stopped must wait for `QB.progressbar.start`'s return, not assume it ended the instant `cancel()` returned.
- **Every-frame polling (`Wait(0)`), not a slower tick.** Unlike `modules/cache`'s configurable `tickInterval` or `modules/zones`' near/far tiering, this can't back off: `DisableControlAction` only suppresses input for the single frame it's called in, so `disable.combat`/`disable.car` would visibly lapse between ticks at any slower interval. The tradeoff (a coroutine resuming every frame for the bar's whole duration) is accepted because a progress bar is inherently short-lived and singular (see the `busy` exclusivity above) — this is not a background loop that accumulates across many concurrent callers the way `modules/cache`'s refresh does.
- **`pcall`-wrapped end to end**, mirroring `modules/nui`'s `withFocus`: `busy` is always reset and `QB.nui.send("progressCancel")` is always sent before a re-raised error propagates, so a native call throwing partway through (bad anim dict, whatever) can't leave the module permanently locked out or the NUI bar stuck on screen.
- **Anim dict load failure degrades, it doesn't abort.** `ensureAnimDict` gives a `RequestAnimDict` up to 5s (`QB.loops.controlled` with exponential backoff, same idiom as `modules/stream`'s loaders) before giving up; a bar whose anim never loads still runs for its full `duration` and can still return `completed = true` — just without the animation. A malformed/missing anim asset shouldn't take down whatever gameplay action the bar represents.
- **No resource-ownership tracking** (unlike `modules/blips`/`modules/cache`, both built on `QB.resources.registry`). A progress bar isn't a handle that outlives the call the way a blip or a cache listener is — it's a synchronous-ish, self-cleaning `pcall`ed call, bounded by `Config.progressbar.maxDuration`. If the calling resource stops mid-bar, the export call itself is what's interrupted (same as any other in-flight export call from that resource); no separate cleanup hook exists for it, matching `modules/stream`'s streaming-asset loaders, which don't hook resource-stop either.

## Best practices
- Check the first return value of `QB.progressbar.start` before treating whatever it was for as done — `completed = false` covers death, the cancel key, and a programmatic `QB.progressbar.cancel()` alike; none of them are errors, they're just "didn't finish."
- Don't call `QB.progressbar.start` again to "retry" immediately after an "already active" rejection without a reason to believe the first one actually ended — `busy` only clears when the running call itself returns.
- Prefer `disable.move` over rolling your own `FreezeEntityPosition` around a bar — it's guaranteed to be unfrozen on every exit path (including an internal error), which a hand-rolled freeze around `QB.progressbar.start` is not.

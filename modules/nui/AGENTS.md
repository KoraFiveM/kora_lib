# nui module guide

## Purpose
This module is the one place every other module talks to the NUI (`web/`) through — focus management, the callback-registration boilerplate, and a promise-based request/response bridge. See the root [AGENTS.md](../../AGENTS.md) "UI conventions" section for the headless-UI rule this module exists to enforce: the NUI renders nothing and holds no focus except in direct response to a message from here.

## Public API
- `Kora.nui.send(action, data)` — thin `SendNUIMessage` wrapper (the capital-NUI table-accepting runtime helper — NOT the `SendNuiMessage` native, which takes a pre-encoded JSON string and would stringify a table into garbage). Every message to the NUI is `{ action, data }`.
- `Kora.nui.setFocus(mouse, keyboard)` — thin `SetNuiFocus` wrapper for callers that need to hold focus across several calls (e.g. a HUD).
- `Kora.nui.withFocus(mouse, keyboard, fn)` — runs `fn` with focus set, always releasing it afterward (even if `fn` errors or the invoking resource stops) — the guaranteed-release path most callers should use instead of `setFocus`.
- `Kora.nui.registerCallback(name, handler)` — wraps `RegisterNUICallback`'s raw `(data, cb)` signature; `handler` just returns a value (or nil).
- `Kora.nui.request(action, data, timeout)` — sends `action` and returns a promise resolving with the NUI's response. `timeout` defaults to 30000ms; pass `false` to disable.
- `Kora.nui.copyToClipboard(text)` — `Kora.nui.request("copyToClipboard", { text = text })`. Resolves `true` on success and `false` on failure/timeout (never rejects); the browser is the only place with real clipboard access.
- `Kora.nui.openMenu(items, title, opts)` / `Kora.nui.openContextMenu(items, x, y)` / `Kora.nui.openRadialMenu(items, opts)` / `Kora.nui.openInputDialog(fields, title, description)` — `Kora.nui.request` wrappers over the NUI's built-in menu/context-menu/radial/input-dialog components (`web/src/components/menu/`, `web/src/components/input/`). `openMenu` optionally takes `position = { horizontal, vertical, offsetX, offsetY }` plus positive pixel `maxWidth`/`maxHeight`; omitting them retains its centred default. Radial items reuse MenuItem and MenuResult, including internal nested submenu paths; radial `opts` accepts an optional positive `radius` — the radial always opens centred on screen. Each acquires an internal mouse+keyboard focus lease for the request's lifetime and releases only that lease when it settles. This keeps an underlying AppShell focused while a nested kora_lib dialog opens and closes. `copyToClipboard` first copies with no focus (ox_lib style); only if the browser refuses does it retry once under a brief cursor-less, input-passthrough lease (`Config.nui.clipboardFocus`, `Config.nui.clipboardUnfocusedFirst`, both default true).
- `Kora.nui.registerApp(definition)` / `openApp(id, opts)` / `updateApp(id, update)` / `closeApp(id?)` / `unregisterApp(id)` / `isAppOpen(id?)` — owner-tracked, declarative full-application shells (`web/src/components/app/AppShell.tsx`). kora_lib owns focus, sidebar navigation, tabs, standard content blocks, action routing, per-app accent lifetime, and close lifecycle; the registering resource owns its definition and `onAction` handler. Only one app shell is active at a time. Each open has the same random response token as other NUI requests, and app actions/updates also carry it so stale or foreign pages cannot invoke handlers or mutate the visible instance.

## Legacy compat
`qb-menu`, `qb-input` and `qb-radialmenu` (standalone resources) are deprecated in favour of `openMenu`/`openInputDialog`/`openRadialMenu` above. `../../compat/client/qb-menu.lua`, `../../compat/client/qb-input.lua` and `../../compat/client/qb-radialmenu.lua` translate those resources' real, public APIs onto `Kora.nui.*` and register under their identities via the same `provideExport`/`__cfx_export_` hijack every compat file in this codebase uses (`kora_target/client/compat/ox-target.lua`, `kora_core/compat/*`). Each calls `Kora.nui.*` directly (not through `exports.kora_lib:...`), so `GetInvokingResource()` inside still resolves to the real external qb-menu/qb-input/qb-radialmenu consumer, not to kora_lib itself. See `docs.md`'s "Legacy compat" section for the field-by-field mapping tables and flagged caveats (dropped icons, `radio`→`select`, and qb-radialmenu's global-persistent-menu-vs-one-shot-`openRadialMenu` mismatch). `closeMenu` sends the normal cancellation response, releases focus, and settles the awaiting request.

## Implementation notes
- **File layout**: client-only, same reasoning as `modules/zones` and `modules/stream` — nothing here crosses the client/server boundary, so no `shared.lua`/`server.lua`.
- **One shared response channel, not one callback per request**: `Kora.nui.request` doesn't register a new `RegisterNUICallback` per call. Every request is tagged with a `requestId`, and a single `kora_lib:nui:response` callback (registered once, at module load) looks that id up in a `pendingRequests` table and resolves/rejects the matching promise. The NUI side is expected to POST its result back to that one callback name, not to a per-request name.
- **Per-request token, not just a sequential `requestId`**: FiveM's NUI-callback routing (the `https://<resource>/<callback>` fetch every NUI page uses) isn't scoped to the frame that issued a given request — another installed resource's own NUI page could in principle spoof a response for a guessable sequential id. Each request also gets a random token from the internal `Kora.compat.generateToken` helper shared with callbacks, events, and minigames; the response handler ignores anything whose `token` doesn't match. The helper seeds its realm's RNG lazily once, never per call — per-call reseeding from a time-derived value would hand two same-millisecond requests identical RNG state and therefore identical "secrets".
- **Timeout is a `SetTimeout`, not `Kora.loops.controlled`**: the duration is already known up front (it's not "poll until some external state changes"), so a single native `SetTimeout(timeout, function() ... end)` per request — the same idiom `local/callback/server.lua` already uses — is both simpler and cheaper than either polling a predicate or spawning a `CreateThread` coroutine that just sits waiting: `SetTimeout` doesn't cost a thread, and this timeout is a safety net that's expected to almost never actually fire (the response callback settles it first).
- **Promises resolve/reject exactly once**: both the response callback and the timeout delete `pendingRequests[requestId]` before settling the promise, so a late response arriving after a timeout (or vice versa) is a no-op rather than a double-resolve.
- **Requests and focus leases are caller-owned**: an invoking-resource stop rejects that owner's pending requests, emits a tokenized `cancelNuiRequest` so the browser drops those surfaces without responding again, and removes only that owner's focus leases. Internal wrappers pass their captured owner through because an asynchronous continuation may no longer expose the original invoking resource.
- **`copyToClipboard` returns a promise like every other request**, not a synchronously-awaited boolean — callers running inside something that can `Citizen.Await` (an NUI callback handler, a command handler) can await it inline; callers that want fire-and-forget can ignore the return value.

## Best practices
- Go through `Kora.nui.request`/`copyToClipboard` rather than `SendNUIMessage`/`RegisterNUICallback` directly — the response-routing and timeout handling only exist once, here.
- Prefer `Kora.nui.withFocus` over `Kora.nui.setFocus` unless you genuinely need focus held across multiple `Kora.nui.request` calls — it's the only version that can't leak focus on an error.
- Keep `Kora.nui.request` timeouts short enough that a player closing the game/resource without responding doesn't leave a caller hanging indefinitely.

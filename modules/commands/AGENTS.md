# commands module guide

## Purpose
A registration wrapper over `RegisterCommand` with owner-tracking (so a resource that restarts doesn't leave dead handlers behind) and chat-suggestion bookkeeping. Moved out of qbcore: none of the registration mechanics touched the framework's player/job model -- the only qbcore-specific pieces were which permission check to run and what to say when a command is denied, both of which are now pluggable (`opts.checkPermission`, `opts.notify`) rather than hardcoded.

## Implementation notes
- **Registry id is the command name, not the resource** -- a genuine bug existed in the pre-move qbcore version: it called `cmdRegistry.track(owner)` with a single argument against an API that requires `track(resource, id)`, so every command from the same resource collapsed onto one `id = nil` slot and the resource-stop sweep's `def.resource == owner` check could never match (the callback receives the disposed *id*, not the resource name). Since `QB.resources.serverRegistry`'s own docs call out exactly this shape ("useful for name-keyed registries... where re-registering an existing name is expected to take it over"), commands now track `(owner, name)` and the dispose callback is handed the command name directly -- no need to scan `commands` for a match.
- **Fail-closed permission default**: if a command declares a non-`'user'` `opts.permission` but no `opts.checkPermission`, it's always denied rather than always allowed. A caller that wants gating has to wire a way to check it; qblib itself has no permission system to fall back on.
- **`opts.notify` defaults to `QB.notify.send`** (qblib's own notify module) for the "no permission" / "missing arguments" messages. A consumer with its own legacy messaging (qbcore uses the old `'QBCore:Notify'` event for compat) overrides it.
- **`QB.commands.remove` now also calls `cmdRegistry.untrack`** -- the pre-move version only cleared the local `commands` table entry, leaving stale registry bookkeeping behind until the owning resource itself stopped. Harmless in practice (a later `track` call for the same name would just overwrite it) but incorrect; fixed here since the registry usage was being corrected anyway.
- **No client-side registration API** -- chat suggestions are pushed to clients via `chat:addSuggestion`/`chat:removeSuggestion`, and there is nothing else for a client realm to do, so this module is server-only.

## Testing
`test/smoke/commands.lua` mocks `RegisterCommand` (capturing the handler by name) and drives it directly to simulate a player running a command. Covers: registration + chat suggestion, permission gating (default fail-closed, an allowing `checkPermission`, custom `notify`), missing-required-args rejection, a handler error being caught rather than propagating, `list`/`refresh`, `remove` untracking, and the resource-stop sweep disposing exactly the commands still owned by the stopped resource (ownership-transfer case included, mirroring `test/smoke/resources.lua`).
